# dsh-access 原账号完整运行链路规格

## 目标

`dsh-access` 作为 DSH Web 的访问管理网关，必须在保留既有数据库和原账号数据的前提下，提供从登录到本机、LAN 和远程协议访问的完整链路。所有受保护的 DSH 请求都经过网关认证、会话、权限和请求策略处理后，才转发到 DSH 上游。

## 数据与账号兼容

- 使用既有数据库副本启动时，不修改 SQLite 文件结构、表、字段、SETUP_KEY 派生值或账号记录。
- 既有原账号可以使用原凭据登录访问管理网关。
- 登录后会话继续使用既有 cookie/session 机制，并遵守账号状态、会话撤销和权限策略。
- 验证或修复不得通过删除数据库、重建原账号或跳过认证来获得通过结果。

## 本机 DSH Web 链路

- 未登录访问网关保护的页面或 API 时，进入访问管理认证边界。
- 原账号登录成功后，网关可以将 DSH Web 页面请求转发到已配置的 DSH 上游。
- 上游响应仍经过现有 HTML 注入、请求策略和会话处理；网关不会把认证后的请求直接暴露为绕过策略的旁路。

## LAN 链路

- 远程状态使用访问管理网关端口生成 LAN 地址和二维码数据。
- 存在可用 LAN IPv4 时，从 LAN 地址访问必须先经过访问管理登录；登录后页面和 API 请求可用。
- LAN 地址不能指向 DSH 上游端口，也不能绕过访问管理网关。
- 没有可用 LAN IPv4 时，状态明确返回空 LAN 字段，并将该环境限制记录为不可执行项，而不是伪造 LAN 通过。

## 远程协议链路

- 访问管理网关支持已认证的 HTTP、SSE 和 WebSocket 请求转发到 DSH 上游。
- 原账号登录后的 HTTP、SSE 和 WebSocket 请求沿用现有身份、封禁、会话撤销、权限和请求策略。
- 未认证的远程协议请求不能直接到达 DSH 上游；HTTP API 按现有约定返回认证响应，页面请求进入登录边界。
- WebSocket 和 SSE 不得因为普通 HTTP 登录保护而被错误地绕过或错误地当作静态页面处理。

## 验证与修复

- 运行期验证必须覆盖原账号登录、本机页面、LAN 入口和 HTTP/SSE/WebSocket 协议转发。
- 发现实现缺陷时，只做满足本规格所需的最小源代码和测试修改。
- 每个修复必须有自动化回归测试或可重复的运行期证据。
- `npm test` 和 `npm run build` 必须通过。
- 既有重命名、许可证、用户界面品牌和远程仓库状态不属于本规格的修改范围。
